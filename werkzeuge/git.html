Erklärung

Vorwissen: keines. Hilfreich ist Linux und Shell, weil Git auf der Kommandozeile bedient wird. Die Ausgaben dieser Seite stammen aus einem echten Repository, das beim Bauen der Website angelegt wird.

Das Problem hinter der Versionsverwaltung

Der Ordner mit analyse_final.R, analyse_final_v2.R und analyse_final_wirklich.R ist bekannt. Er beantwortet keine der Fragen, die später gestellt werden: Was war der Unterschied? Warum wurde das geändert? Mit welcher Fassung ist die Zahl im Bericht entstanden?

Git beantwortet genau diese Fragen. Es speichert nicht Unterschiede, sondern Zustände: Jeder Commit hält den vollständigen Stand fest und verweist auf seinen Vorgänger. Daraus entsteht eine Kette, in der sich jeder frühere Zustand exakt wiederherstellen lässt.

Anlegen und der erste Commit

git("init -q -b main")
schreibe("analyse.R", c("werte <- c(1, 2, 3)", "mean(werte)"))
git("status --short")
?? analyse.R

Das Fragezeichen bedeutet, dass Git die Datei sieht, sie aber noch nicht verfolgt. Der Weg zum Commit führt über zwei Schritte:

git("add analyse.R")
git("status --short")          # jetzt vorgemerkt
A  analyse.R
git("commit -q -m 'Mittelwert berechnen'")
git("log --oneline")
50747f0 Mittelwert berechnen

Warum der Umweg über den Staging-Bereich

Der Zwischenschritt wirkt umständlich und ist der Grund, warum Commits inhaltlich sauber bleiben können. Man wählt aus, was in den nächsten Commit gehört, statt pauschal alles Geänderte einzupacken.

schreibe("analyse.R", c("werte <- c(1, 2, 3, 4)", "mean(werte)", "sd(werte)"))
schreibe("notizen.txt", "unfertige Gedanken")

git("add analyse.R")            # nur diese eine Datei
git("status --short")
M  analyse.R
?? notizen.txt

Die erste Spalte zeigt den Staging-Bereich, die zweite das Arbeitsverzeichnis. M links heisst vorgemerkt, ?? heisst unverfolgt. So lässt sich die fertige Änderung festhalten und die unfertige liegen lassen.

git("commit -q -m 'Standardabweichung ergaenzen'")
git("log --oneline")
89902b5 Standardabweichung ergaenzen
50747f0 Mittelwert berechnen

Ein guter Commit ist eine abgeschlossene Änderung mit einer Nachricht, die das Warum benennt. Fix oder Update sind in einem halben Jahr wertlos; Dezimalkomma beim Import beruecksichtigen ist es nicht.

Was sich geändert hat

schreibe("analyse.R", c("werte <- c(1, 2, 3, 4)", "mean(werte)",
                        "sd(werte)", "median(werte)"))
git("diff --stat")
 analyse.R | 1 +
 1 file changed, 1 insertion(+)
git("diff")
diff --git a/analyse.R b/analyse.R
index ab4a8d2..5f82b67 100644
--- a/analyse.R
+++ b/analyse.R
@@ -1,3 +1,4 @@
 werte <- c(1, 2, 3, 4)
 mean(werte)
 sd(werte)
+median(werte)

Das Minus zeigt die alte Zeile, das Plus die neue. Genau diese Ansicht ist der Grund, warum Textformate versioniert werden können und Binärformate wie Excel-Dateien nicht sinnvoll.

Branches

Ein Branch ist nur ein Zeiger auf einen Commit und deshalb billig. Das macht es sinnvoll, für jeden grösseren Versuch einen anzulegen: Die Hauptlinie bleibt lauffähig, und ein missglückter Versuch wird verworfen statt zurückgebaut.

git("add -A && git -c user.name=B -c user.email=b@example.org commit -q -m 'Median ergaenzen'")
git("switch -q -c experiment-log")
schreibe("analyse.R", c("werte <- c(1, 2, 3, 4)", "mean(log(werte))"))
git("add -A && git -c user.name=B -c user.email=b@example.org commit -q -m 'Log-Transformation testen'")
git("log --oneline --all --graph")
* ca7771a Log-Transformation testen
* 102f845 Median ergaenzen
* 89902b5 Standardabweichung ergaenzen
* 50747f0 Mittelwert berechnen

Die Verzweigung ist im Graphen sichtbar. Zurück auf die Hauptlinie und zusammenführen:

git("switch -q main")
git("merge -q experiment-log -m 'Experiment uebernehmen'")
git("log --oneline")
ca7771a Log-Transformation testen
102f845 Median ergaenzen
89902b5 Standardabweichung ergaenzen
50747f0 Mittelwert berechnen

Konflikte entstehen, wenn dieselbe Stelle auf beiden Seiten geändert wurde. Sie sind normal und müssen inhaltlich entschieden werden; Git markiert die Stelle und überlässt die Entscheidung dem Menschen.

Warum zeigt git status eine Datei als ?? an, obwohl sie im Ordner liegt?

Git verfolgt Dateien nicht automatisch
Richtig. Eine neue Datei ist zunächst unbekannt und wird erst durch git add aufgenommen. Das ist Absicht, sonst landeten Zwischenergebnisse und Zugangsdaten ungewollt im Repository.
Die Datei steht in .gitignore
Dann erschiene sie gar nicht in der Ausgabe.
Der letzte Commit fehlt noch
Der Zustand hat nichts mit dem letzten Commit zu tun, sondern damit, dass die Datei nie vorgemerkt wurde.

Was ist der Unterschied zwischen git add und git commit?

add merkt Änderungen vor, commit schreibt das Vorgemerkte fest
Richtig. Der Zwischenschritt erlaubt es, aus vielen Änderungen im Arbeitsverzeichnis gezielt eine zusammengehörige Auswahl festzuhalten.
add speichert lokal, commit überträgt auf den Server
Beides bleibt lokal. Übertragen wird erst mit push.
add gilt für neue Dateien, commit für geänderte
add wird für beide gebraucht.

Was nicht ins Repository gehört

schreibe(".gitignore", c(".venv/", "renv/library/", "__pycache__/",
                         "data/roh/", "*.Rhistory", ".RData"))
dir.create(file.path(repo, "data", "roh"), recursive = TRUE, showWarnings = FALSE)
schreibe("data/roh/gross.csv", "viele Zeilen")

git("add -A && git -c user.name=B -c user.email=b@example.org commit -q -m 'Ignorierliste'")
git("status --short")           # leer: die Rohdatei wird ignoriert

Die Ausgabe ist leer, obwohl eine neue Datei existiert. Sie wird von der Ignorierliste erfasst.

gehört hinein gehört nicht hinein
Code und Skripte Zugangsdaten und Passwörter
Konfiguration virtuelle Umgebungen
Abhängigkeitslisten grosse Rohdaten
Dokumentation generierte Ausgaben

Ein einmal committetes Passwort bleibt in der Historie, auch wenn die Datei später gelöscht wird. Es muss als kompromittiert gelten und gewechselt werden. Deshalb steht .gitignore am Anfang eines Projekts und nicht am Ende.

Remote und Zusammenarbeit

Das Remote ist eine gleichwertige Kopie, nicht die Wahrheit. Lokal liegt die vollständige Historie, weshalb sich auch ohne Netzverbindung arbeiten lässt.

git remote add origin https://github.com/nutzer/projekt.git
git push -u origin main        # erstmalig, merkt sich die Zuordnung
git pull                       # Aenderungen anderer holen
git clone https://github.com/nutzer/projekt.git    # anderswo auschecken

Notebooks und Git

Ein Punkt, der in der Datenarbeit regelmässig Ärger macht: Jupyter-Notebooks sind JSON und enthalten neben dem Code auch Ausgaben, Bilder und Ausführungszähler. Schon ein erneuter Durchlauf ohne inhaltliche Änderung erzeugt damit einen riesigen Diff.

schreibe("beispiel.ipynb",
         '{"cells": [{"cell_type": "code", "execution_count": 1, "outputs": [{"text": "12.4"}], "source": ["mean(x)"]}]}')
git("add -A && git -c user.name=B -c user.email=b@example.org commit -q -m 'Notebook'")
schreibe("beispiel.ipynb",
         '{"cells": [{"cell_type": "code", "execution_count": 2, "outputs": [{"text": "12.4"}], "source": ["mean(x)"]}]}')
git("diff --stat")
 beispiel.ipynb | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

Der Code ist unverändert, nur der Ausführungszähler ist gestiegen, und trotzdem meldet Git eine Änderung. Wer Ausgaben vor dem Commit leert, bekommt eine lesbare Historie. Der andere Weg ist, die Logik in ein Modul auszulagern, wie in Funktionen und Module in Python beschrieben, und das Notebook schlank zu halten.

In RStudio ist Git über eine Oberfläche eingebaut, usethis::use_git() legt ein Repository an. Die Begriffe sind dieselben; wer die Kommandozeile verstanden hat, findet sich dort sofort zurecht.

Typische Aufgaben

git status                        # Was ist geaendert, was vorgemerkt
git add -p                        # Aenderungen abschnittsweise vormerken
git commit -m "Nachricht"         # Vorgemerktes festschreiben
git log --oneline --graph         # Verlauf kompakt, mit Verzweigungen
git diff                          # Aenderungen im Arbeitsstand
git diff --cached                 # Aenderungen, die vorgemerkt sind
git switch -c thema               # Branch anlegen und wechseln
git merge thema                   # Branch einarbeiten
git restore datei.qmd             # Aenderung an einer Datei verwerfen
git restore --staged datei.qmd    # Vormerkung zuruecknehmen
git revert <commit>               # Commit rueckgaengig machen, mit neuem Commit
git remote -v                     # Verknuepfte Remotes anzeigen
git pull --rebase                 # Fremde Commits unter die eigenen legen

Eine Datei versehentlich eingecheckt, die nicht ins Repository gehört

echo "geheim.env" >> .gitignore
git rm --cached geheim.env
git commit -m "Datei aus der Versionsverwaltung nehmen"

Herausfinden, wann eine Änderung entstanden ist

git log -S "gesuchter Text" --oneline
git blame datei.qmd
