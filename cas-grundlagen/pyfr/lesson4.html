L4 – Exceptions, IO & Serialisierung

Python
Programmiergrundlagen
Reproduzierbarkeit
R
Fehlerbehandlung mit try/except, Dateizugriff mit Encoding und das Speichern von Objekten.

Kernideen aus dem Kurs

  • try / except / else / finally
  • Exception-Typen und eigene Exceptions
  • Dateizugriff mit open und with
  • Text- gegenüber Binärmodus, Encoding
  • Serialisierung: JSON, CSV, Pickle

Erklärung

Vorwissen: L2 – Funktionen & Module für Funktionen, deren Fehlerverhalten hier zum Thema wird, und L3, falls eigene Exception-Klassen definiert werden sollen; sie sind gewöhnliche Klassen.

Fehler als Ausnahme statt als Rückgabewert

Manche Sprachen melden Fehler über einen besonderen Rückgabewert. Das führt dazu, dass nach jedem Aufruf geprüft werden muss, und dass eine vergessene Prüfung stillschweigend mit falschen Werten weiterrechnet.

Python geht den anderen Weg. Eine Funktion liefert entweder ein sinnvolles Ergebnis oder bricht ab. Der Aufrufer darf sich auf das Ergebnis verlassen, und wer den Fehler behandeln will, tut es an einer Stelle:

def zu_zahl(text):
    return int(text)

for eingabe in ["42", "keine Angabe"]:
    try:
        print(zu_zahl(eingabe))
    except ValueError as fehler:
        print(f"nicht verwertbar: {fehler}")
42
nicht verwertbar: invalid literal for int() with base 10: 'keine Angabe'

Die Fehlermeldung kommt vom Interpreter und ist genauer als alles, was man selbst formulieren würde. Sie mitzugeben, statt sie durch eigenen Text zu ersetzen, spart später Zeit bei der Suche.

Nicht zu breit fangen

Ein except ohne Typangabe fängt alles, auch Tippfehler im eigenen Code. Der Fehler verschwindet dann in einer harmlos aussehenden Meldung, statt sich zu zeigen.

def riskant(wert):
    try:
        return 100 / wert
    except Exception:
        return None          # verdeckt jeden Fehler, auch den eigenen

def genau(wert):
    try:
        return 100 / wert
    except ZeroDivisionError:
        return float("inf")  # nur der eine erwartete Fall

print(riskant(0), genau(0))
None inf
print(riskant("text"))       # gibt None, obwohl hier ein Typfehler vorliegt
None

Der letzte Aufruf ist das Problem: Ein Typfehler, der auf einen Fehler weiter oben hinweist, wird zu einem harmlosen None. Die genaue Variante hätte ihn durchgelassen und damit sichtbar gemacht.

Vier Bestandteile stehen zur Verfügung, jeder mit einem klaren Zweck:

Teil wann er läuft wofür
try immer der Code, der scheitern kann
except nur bei passendem Fehler Behandlung
else nur wenn nichts geworfen wurde was vom Gelingen abhängt
finally in jedem Fall Aufräumen 
def lies_zahl(text):
    try:
        wert = int(text)
    except ValueError:
        return None
    else:
        return wert * 2          # nur bei Erfolg
    finally:
        pass                     # hier stuende das Aufraeumen

print(lies_zahl("21"), lies_zahl("x"))
42 None

Verständnisfragen

  1. Warum ist except Exception fast immer zu breit?
  2. Wozu else, wenn der Code auch am Ende des try stehen könnte?
HinweisLösung
  1. Weil es auch Fehler abfängt, mit denen man nicht gerechnet hat, etwa Tippfehler in Namen oder falsche Typen. Diese Fehler zeigen einen Defekt im eigenen Code an und sollen laut scheitern statt still behandelt zu werden. Gefangen gehört nur, was man erwartet und sinnvoll behandeln kann.
  2. Weil im try möglichst wenig stehen soll. Alles darin ist Kandidat für den except-Zweig; steht dort auch Folgecode, könnte dessen Fehler versehentlich als der erwartete behandelt werden. else trennt sauber zwischen dem, was schiefgehen darf, und dem, was daraufhin passiert.

Dateien lesen und schreiben

Der with-Block ist der Normalfall, weil er die Datei auch dann schliesst, wenn im Block ein Fehler auftritt. Ohne ihn bleibt bei einem Abbruch ein offener Dateizeiger zurück.

pfad = arbeitsordner / "messung.txt"

with open(pfad, "w", encoding="utf-8") as f:
    f.write("Drossel;12.4\nVentil;9.8\n")
24
with open(pfad, encoding="utf-8") as f:
    for zeile in f:
        name, wert = zeile.strip().split(";")
        print(f"{name:10s} {float(wert):6.1f}")
Drossel      12.4
Ventil        9.8

Encoding ist keine Nebensache

Der zweite Punkt kostet in gemischten Umgebungen regelmässig Zeit. Ohne Angabe verwendet Python die Voreinstellung des Betriebssystems, und die ist unter Windows eine andere als unter Linux. Umlaute werden dann beim Lesen zu Kauderwelsch oder lösen einen Fehler aus.

pfad = arbeitsordner / "umlaute.txt"
pfad.write_text("Grösse: 12 µm", encoding="utf-8")
13
# richtig gelesen
print(pfad.read_text(encoding="utf-8"))
Grösse: 12 µm
# mit falscher Annahme
try:
    print(pfad.read_text(encoding="ascii"))
except UnicodeDecodeError as fehler:
    print("falsches Encoding:", fehler)
falsches Encoding: 'ascii' codec can't decode byte 0xc3 in position 2: ordinal not in range(128)

Regel ohne Ausnahme: encoding="utf-8" immer ausdrücklich angeben, beim Schreiben wie beim Lesen. Das kostet zwölf Zeichen und verhindert eine ganze Fehlerklasse, die typischerweise erst auffällt, wenn jemand anders die Datei öffnet.

Serialisierung: drei Formate, drei Zwecke

Serialisierung heisst, ein Objekt in eine Form zu bringen, die sich speichern und wieder einlesen lässt.

Format speichert lesbar für Grenze
JSON einfache Typen Mensch und andere Sprachen keine eigenen Objekte, keine Datumstypen
CSV Tabellen Mensch und Tabellenkalkulation verliert jede Typinformation
Pickle fast beliebige Python-Objekte nur Python unsicher aus fremder Quelle 
konfig = {"schwelle": 12.5, "aktiv": True, "orte": ["Bern", "Chur"]}

pfad = arbeitsordner / "konfig.json"
with open(pfad, "w", encoding="utf-8") as f:
    json.dump(konfig, f, ensure_ascii=False, indent=2)

print(pfad.read_text(encoding="utf-8"))
{
  "schwelle": 12.5,
  "aktiv": true,
  "orte": [
    "Bern",
    "Chur"
  ]
}
with open(pfad, encoding="utf-8") as f:
    zurueck = json.load(f)
print(zurueck == konfig)
True

Das Argument ensure_ascii=False sorgt dafür, dass Umlaute als Zeichen gespeichert werden statt als Fluchtsequenzen. Lesbarkeit ist bei Konfigurationsdateien der halbe Zweck.

Was JSON nicht kann, zeigt sich bei Typen, die es nicht kennt:

import datetime

try:
    json.dumps({"zeitpunkt": datetime.date(2026, 3, 1)})
except TypeError as fehler:
    print("JSON kennt keine Datumstypen:", fehler)
JSON kennt keine Datumstypen: Object of type date is not JSON serializable
# ueblicher Ausweg: als Zeichenkette speichern
print(json.dumps({"zeitpunkt": datetime.date(2026, 3, 1).isoformat()}))
{"zeitpunkt": "2026-03-01"}

Pickle darf niemals aus unbekannter Quelle geladen werden. Beim Laden wird Code ausgeführt, eine präparierte Datei kann also beliebige Befehle absetzen. Für eigene Zwischenstände ist es in Ordnung, für Austausch nicht.

  • R
  • Python
ergebnis <- tryCatch({
  as.numeric("nicht-zahl")
}, warning = function(w) NA_real_)

pfad <- tempfile(fileext = ".rds")
saveRDS(list(a = 1, b = "text"), pfad)     # R-eigenes Format, wie Pickle
str(readRDS(pfad))
List of 2
 $ a: num 1
 $ b: chr "text"
# JSON braucht ein Paket, ist dafuer sprachuebergreifend
# jsonlite::write_json(list(a = 1), "konfig.json")
import pickle

pfad = arbeitsordner / "zwischenstand.pkl"
with open(pfad, "wb") as f:                 # Binaermodus!
    pickle.dump({"a": 1, "b": "text"}, f)

with open(pfad, "rb") as f:
    print(pickle.load(f))
{'a': 1, 'b': 'text'}

Die Entsprechung ist genau: saveRDS in R und Pickle in Python speichern sprachspezifisch und vollständig, JSON und CSV speichern sprachneutral und eingeschränkt. Das b im Modus steht für binär und ist bei Pickle Pflicht.

Verständnisfragen

  1. Wann ist Pickle gegenüber JSON gerechtfertigt?
  2. Eine CSV-Datei enthält die Spalte id mit Werten wie 007. Was passiert beim Einlesen und Zurückschreiben?
HinweisLösung
  1. Für kurzlebige eigene Zwischenstände, etwa ein zwischengespeichertes Modellobjekt oder einen Rechenschritt, der lange dauert. Sobald die Datei weitergegeben, langfristig aufbewahrt oder von einer anderen Sprache gelesen werden soll, ist JSON oder ein Tabellenformat richtig.
  2. Die führenden Nullen gehen verloren, sobald die Spalte als Zahl erkannt wird; aus 007 wird 7. Beim Zurückschreiben steht dann ein anderer Wert in der Datei als vorher. CSV trägt keine Typinformation, deshalb muss der Typ beim Einlesen vorgegeben werden.
