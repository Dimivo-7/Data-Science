Ein Name ist kein Behälter

In vielen Sprachen deklariert man eine Variable mit einem Typ, und dieser Typ gilt. Python macht es anders: Ein Name ist nur ein Verweis auf ein Objekt, und derselbe Name kann nacheinander auf Objekte ganz verschiedener Art zeigen.

x = 42
print(type(x))
<class 'int'>
x = "jetzt Text"
print(type(x))
<class 'str'>

Das macht den Einstieg schnell und verschiebt Fehler von der Übersetzungs- in die Laufzeit. Ein Tippfehler in einem Namen fällt erst auf, wenn die Zeile ausgeführt wird, und das kann in einem selten betretenen Zweig lange dauern.

Die Konsequenz für die Praxis: früh und oft ausführen, statt lange zu schreiben und dann zu starten.

Die vier Container

Für die tägliche Arbeit genügen vier Sammlungstypen. Die Wahl zwischen ihnen ist keine Geschmacksfrage, sondern hängt daran, was gebraucht wird.

Typ geordnet veränderlich Zugriff über wofür
Liste ja ja Position der Normalfall
Tupel ja nein Position feste Wertegruppen, Rückgabe mehrerer Werte
Dictionary ja (Einfügung) ja Schlüssel benannte Daten
Set nein ja nur Mitgliedschaft Eindeutigkeit, Mengenoperationen
  • R
  • Python
# Vektor als Gegenstueck zur Liste, benannte Liste zum Dictionary
werte <- c(3, 1, 4, 1, 5)
werte[2]                       # R zaehlt ab 1
[1] 1
person <- list(name = "Ada", jahr = 1815)
person$name
[1] "Ada"
unique(werte)                  # Gegenstueck zum Set
[1] 3 1 4 5
werte = [3, 1, 4, 1, 5]
print(werte[1])                # Python zaehlt ab 0
1
person = {"name": "Ada", "jahr": 1815}
print(person["name"])
Ada
print(set(werte))              # Duplikate fallen weg
{1, 3, 4, 5}

Der Indexunterschied ist die häufigste Stolperstelle beim Wechsel zwischen den Sprachen. R beginnt bei eins, Python bei null. Beim Slicing kommt hinzu, dass in Python die obere Grenze nicht enthalten ist: werte[0:2] liefert zwei Elemente, nicht drei.

werte = [3, 1, 4, 1, 5]
print(werte[0:2])      # Position 0 und 1
[3, 1]
print(werte[:3])       # von vorne
[3, 1, 4]
print(werte[-1])       # das letzte
5
print(werte[::-1])     # rueckwaerts
[5, 1, 4, 1, 3]

Veränderlich oder nicht

Der Unterschied zwischen Liste und Tupel wirkt nebensächlich und hat handfeste Folgen. Eine Liste lässt sich nach dem Anlegen ändern, ein Tupel nicht. Weil ein Dictionary-Schlüssel unveränderlich sein muss, kann ein Tupel als Schlüssel dienen, eine Liste nicht.

liste = [1, 2, 3]
liste[0] = 99
print(liste)
[99, 2, 3]
tupel = (1, 2, 3)
try:
    tupel[0] = 99
except TypeError as fehler:
    print("Tupel:", fehler)
Tupel: 'tuple' object does not support item assignment
# deshalb funktioniert das hier
koordinaten = {(47.3, 8.5): "Zürich", (46.9, 7.4): "Bern"}
print(koordinaten[(46.9, 7.4)])
Bern

Daraus folgt eine der bekanntesten Fallen. Weil ein Name nur ein Verweis ist, zeigen zwei Namen nach einer Zuweisung auf dasselbe Objekt:

a = [1, 2, 3]
b = a               # kein neues Objekt, nur ein zweiter Verweis
b.append(4)
print("a:", a)      # a hat sich mitveraendert
a: [1, 2, 3, 4]
c = a.copy()        # jetzt eine echte Kopie
c.append(5)
print("a:", a, " c:", c)
a: [1, 2, 3, 4]  c: [1, 2, 3, 4, 5]

Verständnisfragen

  1. Warum liefert werte[0:2] zwei und nicht drei Elemente?
  2. Wann ist ein Tupel der Liste vorzuziehen?
HinweisLösung
  1. Weil Python die obere Grenze ausschliesst. Der Vorteil dieser Konvention ist, dass die Länge des Ausschnitts direkt die Differenz der beiden Zahlen ist und dass werte[:k] und werte[k:] zusammen genau die ganze Liste ergeben, ohne Überlappung.
  2. Wenn die Werte inhaltlich zusammengehören und sich nicht ändern sollen, etwa ein Koordinatenpaar oder die Rückgabe mehrerer Werte aus einer Funktion. Ausserdem immer dann, wenn die Gruppe als Dictionary-Schlüssel dienen soll, denn dafür wird Unveränderlichkeit verlangt.

Kontrollfluss und Einrückung

Python bildet Blöcke nicht mit Klammern, sondern mit Einzug. Das erzwingt lesbaren Code und bestraft gemischte Tabulatoren und Leerzeichen sofort.

werte = [12, 45, 7, 31, 88]

for w in werte:
    if w > 40:
        art = "hoch"
    elif w > 10:
        art = "mittel"
    else:
        art = "tief"
    print(f"{w:>3} -> {art}")
 12 -> mittel
 45 -> hoch
  7 -> tief
 31 -> mittel
 88 -> hoch

Das f vor der Zeichenkette markiert eine f-String-Formatierung: Ausdrücke in geschweiften Klammern werden ausgewertet und eingesetzt, :>3 richtet rechtsbündig auf drei Stellen aus.

Comprehensions

Eine Schleife, die nichts tut, als eine Liste zu füllen, lässt sich kürzer und schneller schreiben. Das ist kein Stilmittel, sondern die idiomatische Form:

werte = [12, 45, 7, 31, 88]

# umstaendlich
quadrate = []
for w in werte:
    quadrate.append(w ** 2)

# idiomatisch
quadrate_kurz = [w ** 2 for w in werte]
print(quadrate == quadrate_kurz)
True
# mit Bedingung
print([w for w in werte if w > 30])
[45, 31, 88]
# auch fuer Dictionaries
print({w: w ** 2 for w in werte if w < 20})
{12: 144, 7: 49}

Der Vergleich zu R liegt nahe. Dort erledigt die Vektorisierung dasselbe, ohne dass überhaupt eine Schleifenkonstruktion sichtbar wird:

  • R
  • Python
werte <- c(12, 45, 7, 31, 88)

werte^2                # elementweise, ohne Schleife
[1]  144 2025   49  961 7744
werte[werte > 30]      # Filtern ueber einen logischen Vektor
[1] 45 31 88
werte = [12, 45, 7, 31, 88]

print([w ** 2 for w in werte])
[144, 2025, 49, 961, 7744]
print([w for w in werte if w > 30])
[45, 31, 88]

Ohne NumPy braucht Python die Comprehension, weil eine Liste keine Rechenoperationen elementweise unterstützt. Mit NumPy, siehe L6, verhält sich Python dann wie R.

werte = [1, 2, 3]
print(werte * 2)        # verdoppelt die Liste, multipliziert nicht!
[1, 2, 3, 1, 2, 3]

Diese Zeile ist ein klassischer Stolperstein: Der Stern wiederholt die Liste, statt ihre Elemente zu multiplizieren.

Verständnisfragen

  1. Was ergibt [0] * 3 und was [w * 3 for w in [0]]?
  2. Warum ist eine Comprehension der gefüllten Schleife vorzuziehen?
HinweisLösung
  1. Das erste ergibt [0, 0, 0], also eine dreimal wiederholte Liste. Das zweite ergibt [0], weil das eine Element mit drei multipliziert wird. Der Stern bedeutet bei Listen Wiederholung, nicht Rechnung.
  2. Weil die Absicht direkt lesbar ist und der Interpreter die Schleife intern ausführt, was schneller ist als wiederholtes append. Ausserdem entfällt die leere Liste als Zwischenschritt, die man vergessen oder falsch benennen kann.

Wo man arbeitet

Vier Umgebungen, die verschiedene Zwecke bedienen und keine Rangfolge bilden.

Umgebung wofür sie taugt Grenze
Konsole einzelne Ausdrücke ausprobieren nichts bleibt erhalten
Jupyter Analyse mit Text, Code und Ausgabe in einem Dokument Ausführungsreihenfolge kann von der Lesereihenfolge abweichen
Spyder Skripte mit Variablenübersicht, nahe an RStudio weniger für grosse Projekte
PyCharm mehrere Dateien, Tests, Refactoring schwergewichtig für eine kurze Auswertung

Die Falle bei Notebooks ist real. Wer Zellen in beliebiger Reihenfolge ausführt, erzeugt einen Zustand, der sich beim Durchlauf von oben nicht reproduzieren lässt. Die Probe ist derselbe Reflex wie in RStudio: Kernel neu starten und alles von oben ausführen. Läuft es dann nicht durch, war das Ergebnis nie reproduzierbar.
