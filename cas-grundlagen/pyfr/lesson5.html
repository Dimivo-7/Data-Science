Erklärung

Vorwissen: L2 – Funktionen & Module, weil ein Paket nichts anderes ist als eine geordnete Sammlung von Modulen. Diese Seite ist die Voraussetzung für alles Weitere, denn NumPy, Pandas und Matplotlib müssen irgendwo herkommen.

Das Problem, das virtuelle Umgebungen lösen

Zwei Projekte, beide brauchen dieselbe Bibliothek, aber in verschiedenen Versionen. Das ältere läuft nur mit der alten, das neue nutzt eine Funktion, die es erst in der neuen gibt. Wird global installiert, gibt es nur einen Stand, und eines der beiden Projekte ist immer kaputt.

Die zweite Hälfte des Problems zeigt sich später: Eine Auswertung, die vor einem Jahr lief, liefert heute andere Zahlen oder bricht ab, weil eine Bibliothek ihr Verhalten geändert hat. Ohne festgehaltene Versionen ist eine Analyse nur so lange nachvollziehbar, bis jemand etwas aktualisiert.

Eine virtuelle Umgebung ist die Antwort auf beides: ein eigenes Verzeichnis mit eigenem Interpreter und eigenen Paketen, das zu genau einem Projekt gehört.

Modul, Paket, Distribution

Drei Begriffe, die im Alltag durcheinandergehen und Verwirrung stiften, sobald eine Installation nicht klappt.

Begriff was es ist Beispiel
Modul eine .py-Datei json
Paket ein Verzeichnis von Modulen numpy
Distribution das, was installiert wird scikit-learn

Der Fallstrick: Der Name, unter dem installiert wird, muss nicht dem Importnamen entsprechen. Installiert wird scikit-learn, importiert wird sklearn. Wer nach dem Importnamen sucht, findet das Paket nicht.

import json                       # Modul der Standardbibliothek
import numpy as np                # Paket, mit Alias importiert
from pathlib import Path          # nur ein Name aus einem Modul

print(json.__name__, np.__version__, Path.__name__)
json 2.5.3 Path

Der Alias np ist Konvention, keine Vorschrift. Er hat sich durchgesetzt, weil NumPy-Code sonst unlesbar wird, und man sollte ihn deshalb nicht abwandeln.

Wo Python nachschaut

Ein Import durchsucht eine Liste von Verzeichnissen in fester Reihenfolge. Das erklärt den häufigsten Anfängerfehler:

print(sys.executable)          # welcher Interpreter laeuft gerade
/opt/hostedtoolcache/Python/3.12.14/x64/bin/python
for eintrag in sys.path[:4]:
    print(" ", eintrag or "(aktuelles Verzeichnis)")
  (aktuelles Verzeichnis)
  /opt/hostedtoolcache/Python/3.12.14/x64/bin
  /opt/hostedtoolcache/Python/3.12.14/x64/lib/python312.zip
  /opt/hostedtoolcache/Python/3.12.14/x64/lib/python3.12

Das aktuelle Verzeichnis steht vorne. Eine eigene Datei namens random.py im Projektordner verdeckt deshalb das gleichnamige Modul der Standardbibliothek, und die Fehlermeldung deutet auf alles Mögliche, nur nicht auf den wahren Grund.

Regel: Eigene Dateien nie so benennen wie ein Paket, das man verwendet. Also kein numpy.py, kein json.py, kein random.py im Projektordner.

Umgebung anlegen und benutzen

Diese Befehle laufen in der Shell, nicht im Interpreter, und sind deshalb als reines Listing gesetzt:

python -m venv .venv                 # Umgebung im Projektordner anlegen

.venv\Scripts\activate               # aktivieren unter Windows
source .venv/bin/activate            # aktivieren unter Linux und macOS

pip install numpy pandas matplotlib
pip list                             # was ist drin
deactivate                           # wieder verlassen

Ob die Aktivierung gewirkt hat, verrät der Interpreterpfad. Er zeigt nach dem Aktivieren in den Projektordner statt auf die systemweite Installation:

print(sys.executable)
/opt/hostedtoolcache/Python/3.12.14/x64/bin/python
print("Version:", sys.version.split()[0])
Version: 3.12.14

Das Verzeichnis .venv gehört in .gitignore. Versioniert wird die Liste der Abhängigkeiten, nicht ihr installierter Inhalt. Sie ist klein, lesbar und erzeugt die Umgebung anderswo neu; das Verzeichnis selbst wäre gross, plattformabhängig und im Diff wertlos.

Abhängigkeiten festhalten

Der eigentliche Zweck ist Reproduzierbarkeit. Was installiert ist, lässt sich auslesen und später wiederherstellen:

pip freeze > requirements.txt        # was ist installiert, mit Versionen
pip install -r requirements.txt      # anderswo dasselbe herstellen

Der Unterschied zwischen zwei Schreibweisen entscheidet darüber, wie verlässlich das ist:

Zeile in der Datei Bedeutung wann sinnvoll
pandas irgendeine Version fast nie
pandas>=2.0 mindestens diese Bibliotheken, die andere einbinden
pandas==2.2.1 genau diese Auswertungen, die reproduzierbar bleiben sollen

Für eine Semesterarbeit oder eine Analyse, die in einem Jahr noch dieselben Zahlen liefern soll, ist die dritte Zeile die richtige.

for paket in ["numpy", "pandas", "matplotlib"]:
    print(f"{paket}=={importlib.metadata.version(paket)}")
numpy==2.5.3
pandas==3.0.5
matplotlib==3.11.1

Diese Ausgabe stammt aus der Umgebung, die diese Website baut. Genau solche Zeilen gehören in die Abhängigkeitsliste.

pip oder conda

Beide installieren Pakete, unterscheiden sich aber im Umfang.

pip installiert aus PyPI und kümmert sich um Python-Pakete. Für die allermeisten Fälle genügt es, und es ist ohne Zusatzinstallation vorhanden.

conda, meist über Anaconda, verwaltet zusätzlich nicht-pythonische Bestandteile, etwa kompilierte numerische Bibliotheken. Bei Paketen, die gegen C- oder Fortran-Code gebaut sind, erspart das früher regelmässig Übersetzungsprobleme. Heute liefert PyPI für gängige Pakete fertige Binärdateien mit, wodurch dieser Vorteil kleiner geworden ist.

Beide in derselben Umgebung zu mischen ist eine bekannte Quelle kaputter Installationen, weil jedes Werkzeug nur seine eigene Buchführung kennt. Pro Projekt eines wählen und dabei bleiben.

# renv erfuellt denselben Zweck: Isolation je Projekt
# renv::init()                # Projektbibliothek anlegen
# install.packages("dplyr")
# renv::snapshot()            # Versionen in renv.lock festhalten
# renv::restore()             # Umgebung anderswo wiederherstellen

# Was gerade geladen ist, samt Versionen
head(as.data.frame(installed.packages()[, c("Package", "Version")]), 4)
            Package Version
base64enc base64enc   0.1-6
bit             bit   4.6.0
bit64         bit64   4.8.6
blob           blob   1.3.0
import importlib.metadata as md

pakete = sorted((d.metadata["Name"], d.version)
                for d in md.distributions())[:4]
for name, version in pakete:
    print(f"{name:20s} {version}")
contourpy            1.3.3
cycler               0.12.1
fonttools            4.64.0
formulaic            1.2.2

Die Entsprechung ist eng: renv.lock ist die requirements.txt von R, renv::restore() das Gegenstück zu pip install -r. Wer eines kennt, versteht das andere sofort.

Verständnisfragen

  1. Warum gehört .venv in .gitignore, requirements.txt aber ins Repository?
  2. Eine Auswertung lief letztes Jahr, heute bricht sie ab. Was ist der erste Verdacht, und was hätte es verhindert?
NoteLösung
  1. Weil das Verzeichnis den installierten Inhalt enthält, also hunderte Megabyte plattformabhängiger Dateien, die sich aus der Liste jederzeit neu erzeugen lassen. Die Liste dagegen ist die eigentliche Information, klein und lesbar, und gehört zum Code wie das Skript selbst.
  2. Eine Bibliothek hat ihr Verhalten geändert, weil sie zwischenzeitlich aktualisiert wurde. Verhindert hätte es eine virtuelle Umgebung mit exakt festgeschriebenen Versionen, sodass beim Wiederherstellen genau derselbe Stand entsteht.
