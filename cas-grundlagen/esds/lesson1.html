Erklärung

Vorwissen: keines. Diese Seite ist der Einstieg in ESDS und setzt weder Statistik noch Programmiererfahrung voraus. Wer sie durchgearbeitet hat, kann mit L2 – Data Wrangling mit dem Tidyverse weitermachen; die Datenstrukturen von hier tauchen dort auf jeder Zeile wieder auf.

Wozu eine eigene Sprache für Daten

Eine Tabellenkalkulation kommt weit. Sie stösst dort an ihre Grenze, wo eine Auswertung wiederholbar sein soll: Wer im Frühling dieselbe Analyse mit neuen Zahlen braucht, klickt sie erneut zusammen und weiss hinterher nicht sicher, ob er dieselben Schritte in derselben Reihenfolge erwischt hat. Ein Skript beantwortet diese Frage, weil jeder Schritt darin nachlesbar ist.

R ist für genau diesen Zweck entstanden, nicht als allgemeine Programmiersprache mit angebauter Statistik. Das erklärt einige Eigenheiten, die zunächst ungewohnt wirken und später Arbeit sparen.

Alles ist ein Vektor

Angenommen, fünfhundert Messwerte sollen von Millimeter in Zentimeter umgerechnet werden. In vielen Sprachen schreibt man dafür eine Schleife, die jeden Wert einzeln anfasst. In R entfällt dieser Schritt, weil die Grundstruktur nicht die einzelne Zahl ist, sondern die Folge von Zahlen.

Auch ein einzelner Wert ist bereits eine solche Folge, nur mit der Länge eins. Das lässt sich direkt nachsehen:

  • R
  • Python
x <- 5          # sieht aus wie eine einzelne Zahl
length(x)       # ist aber ein Vektor der Laenge 1
[1] 1
is.vector(x)
[1] TRUE
x = 5           # hier wirklich eine einzelne Zahl
print(type(x))
<class 'int'>
# Die Entsprechung entsteht erst durch NumPy oder pandas:
print(np.array([5]).shape)
(1,)

Der Unterschied zwischen den Sprachen ist an dieser Stelle grundsätzlich. R bringt das Rechnen mit ganzen Folgen von Haus aus mit, Python holt es sich über eine Bibliothek dazu. Für die tägliche Arbeit läuft es auf dasselbe hinaus, beim Lesen fremden Codes hilft es, den Unterschied zu kennen.

Aus dieser Grundentscheidung folgt, dass Rechenoperationen elementweise auf den ganzen Vektor wirken:

  • R
  • Python
werte <- c(12, 45, 7, 31)
werte / 10        # jeder Wert wird geteilt
[1] 1.2 4.5 0.7 3.1
werte > 20        # Vergleich liefert wieder einen Vektor, diesmal logisch
[1] FALSE  TRUE FALSE  TRUE
sum(werte > 20)   # TRUE zaehlt als 1, FALSE als 0
[1] 2
werte = np.array([12, 45, 7, 31])
print(werte / 10)
[1.2 4.5 0.7 3.1]
print(werte > 20)
[False  True False  True]
print((werte > 20).sum())
2

Der letzte Ausdruck lohnt einen zweiten Blick, weil er ein Muster zeigt, das später ständig auftaucht. werte > 20 liefert keinen einzelnen Wahrheitswert, sondern für jeden Messwert einen. Summiert man diese Wahrheitswerte, zählt R die Treffer, weil TRUE beim Rechnen als 1 gilt. Aus einer Bedingung wird so eine Anzahl, ohne dass eine Schleife nötig wäre.

Faustregel für den Anfang: Wer in R eine Schleife über Zahlen schreibt, sollte kurz innehalten. In den allermeisten Fällen gibt es eine vektorisierte Schreibweise, die kürzer und schneller ist.

Was liefert c(2, 4, 6) * c(10, 20, 30)?

Die Zahl 280, also das Skalarprodukt
R fasst die beiden nicht als mathematische Vektoren auf. Für das Skalarprodukt gäbe es %*%.
Den Vektor 20 80 180
Richtig. Multipliziert wird paarweise, erstes mit erstem und so weiter. Fast jede Operation in R arbeitet Position für Position.
Einen Fehler wegen fehlender Schleife
Genau die ist nicht nötig. Die elementweise Rechnung ist in R der Normalfall.

Bei den Werten 12, 45, 7, 31 ergibt mean(werte > 20) den Wert 0.5. Was sagt diese Zahl inhaltlich?

Der Mittelwert der Messwerte beträgt 0.5
Gemittelt wird nicht über die Messwerte, sondern über das Ergebnis des Vergleichs.
Die Hälfte der Messwerte liegt über 20
Richtig. Der Vergleich liefert Wahrheitswerte, und deren Mittelwert ist der Anteil der wahren Fälle. Dasselbe wie sum(...), nur durch die Anzahl geteilt.
Es gibt 0.5 Werte über 20
Eine Anzahl kann nicht gebrochen sein. Für die Anzahl müsste sum statt mean stehen.

Recycling: bequem, bis es weh tut

Was passiert, wenn zwei Vektoren unterschiedlich lang sind? R bricht nicht ab, sondern wiederholt den kürzeren so oft, bis er zum längeren passt. Bei werte / 10 ist das der Grund, warum die einzelne 10 auf alle vier Werte angewendet wird.

Das ist die bequeme Seite. Die unbequeme zeigt sich, sobald die Längen unbeabsichtigt nicht zusammenpassen:

  • R
  • Python
lang <- c(1, 2, 3, 4, 5, 6)
kurz <- c(10, 100)

lang * kurz     # kurz wird zu 10, 100, 10, 100, 10, 100 aufgefuellt
[1]  10 200  30 400  50 600
lang = np.array([1, 2, 3, 4, 5, 6])
kurz = np.array([10, 100])

try:
    lang * kurz
except ValueError as fehler:
    print("NumPy bricht ab:", fehler)
NumPy bricht ab: operands could not be broadcast together with shapes (6,) (2,)

Beide Ergebnisse sind lehrreich. R liefert klaglos sechs Zahlen, obwohl die Absicht vermutlich eine andere war. NumPy verweigert die Rechnung, weil die Formen nicht zusammenpassen. Die Regel, nach der NumPy Formen doch angleicht, heisst Broadcasting und ist enger gefasst als das Recycling in R: Sie greift nur, wenn eine der beteiligten Achsen die Länge eins hat.

Für R heisst das praktisch, dass eine Kontrolle vor der Rechnung lohnt, wo die Längen nicht offensichtlich gleich sind:

length(lang)
[1] 6
length(kurz)
[1] 2
# stopifnot bricht ab, sobald die Annahme nicht mehr stimmt:
stopifnot(length(lang) == 6)

Ein Vektor, ein Typ

Eine Spalte, die plötzlich Text enthält statt Zahlen, gehört zu den häufigsten Stolpersteinen beim Einlesen von Daten. Die Ursache liegt fast immer in einer Regel, die R still anwendet: Ein Vektor trägt genau einen Typ. Treffen verschiedene Typen aufeinander, vereinheitlicht R sie zum allgemeineren, statt einen Fehler zu melden. Dieser Vorgang heisst Coercion.

Die Rangfolge lässt sich in drei Schritten nachvollziehen:

class(c(TRUE, FALSE))          # logisch
[1] "logical"
class(c(TRUE, 3))              # logisch trifft Zahl  -> Zahl
[1] "numeric"
class(c(TRUE, 3, "drei"))      # Zahl trifft Text     -> Text
[1] "character"

Im letzten Fall ist aus der 3 die Zeichenkette "3" geworden. Rechnen lässt sich damit nicht mehr, und genau das merkt man oft erst mehrere Schritte später:

gemischt <- c(1, 2, "3")
gemischt
[1] "1" "2" "3"
sum(as.numeric(gemischt))      # erst nach ausdruecklicher Umwandlung
[1] 6

Ein einziger auffälliger Eintrag in einer CSV-Spalte, etwa ein Strich für einen fehlenden Wert, reicht also aus, um die ganze Spalte in Text zu verwandeln. Deshalb steht in L2 die Kontrolle der Spaltentypen direkt hinter dem Import.

Welchen Wert hat das dritte Element von c(1, 2, TRUE)?

Die Zahl 1
Richtig. Ein Vektor trägt nur einen Typ, und Zahlen sind allgemeiner als Wahrheitswerte. TRUE wird deshalb zu 1, der Vektor lautet 1 2 1.
Der Text "TRUE"
Zu Text wird erst umgewandelt, wenn ein Textwert beteiligt ist. Hier gibt es keinen.
TRUE, der Vektor bleibt gemischt
Gemischte Typen sind in einem Vektor nicht möglich. Genau das unterscheidet ihn von einer Liste.

Eine eingelesene Spalte enthält "1.234", gemeint war die Zahl 1234. as.numeric meldet keinen Fehler. Warum ist das besonders unangenehm?

Weil die Umwandlung fehlschlägt und NA liefert
Sie schlägt gerade nicht fehl. Ein NA wäre auffällig gewesen.
Weil 1.234 eine gültige Zahl ist und die Rechnung stillschweigend um den Faktor 1000 danebenliegt
Richtig. R liest den Punkt als Dezimaltrennzeichen. Die Ursache liegt im Import, nicht in der Umwandlung.
Weil R den Punkt nicht kennt
R kennt ihn sehr wohl, nur eben als Dezimaltrennzeichen und nicht als Tausendertrennung.

Faktoren: Kategorien mit Gedächtnis

Kategoriale Merkmale wie Standort, Gerätetyp oder Antwortstufen liessen sich als Text speichern. Damit ginge aber verloren, welche Ausprägungen überhaupt möglich sind. Eine Umfrage mit den Antwortmöglichkeiten ja, nein und weiss nicht bleibt vollständig zu berichten, auch wenn niemand die dritte gewählt hat. Text kann das nicht abbilden, weil er nur enthält, was tatsächlich vorkommt.

Der Faktor löst das, indem er die möglichen Stufen als eigene Eigenschaft mitführt:

  • R
  • Python
antworten <- c("ja", "nein", "ja", "ja", "nein")

als_faktor <- factor(antworten, levels = c("ja", "nein", "weiss nicht"))
levels(als_faktor)
[1] "ja"          "nein"        "weiss nicht"
table(als_faktor)          # die unbesetzte Stufe erscheint mit 0
als_faktor
         ja        nein weiss nicht 
          3           2           0 
antworten = ["ja", "nein", "ja", "ja", "nein"]

als_kategorie = pd.Categorical(antworten,
                               categories=["ja", "nein", "weiss nicht"])
print(als_kategorie.categories.tolist())
['ja', 'nein', 'weiss nicht']
print(pd.Series(als_kategorie).value_counts())
ja             3
nein           2
weiss nicht    0
Name: count, dtype: int64

Der Unterschied wird in der Darstellung sichtbar. In Abbildung 1 steht links die vollständige Skala mit allen drei Antwortmöglichkeiten, rechts nur das, was zufällig in den Daten vorkommt:

  • R
  • Python
ohne_vorgabe <- factor(antworten)

par(mfrow = c(1, 2), mar = c(4, 4, 3, 1))
barplot(table(als_faktor), col = "grey75", ylim = c(0, 3),
        main = "levels vorgegeben", ylab = "Anzahl")
barplot(table(ohne_vorgabe), col = "grey75", ylim = c(0, 3),
        main = "levels aus den Daten")
# reindex mit dem Kategorienobjekt statt mit einer Stringliste:
# so kann der Index nicht am Typ vorbeilaufen
mit = (pd.Series(als_kategorie).value_counts()
         .reindex(als_kategorie.categories).fillna(0))
ohne = pd.Series(antworten).value_counts()

fig, (a, b) = plt.subplots(1, 2, sharey=True, figsize=(7, 3.2))
a.bar(list(mit.index), mit.values, color="0.75")
a.set_title("categories vorgegeben")
a.set_ylabel("Anzahl")
b.bar(list(ohne.index), ohne.values, color="0.75")
b.set_title("categories aus den Daten")
fig.tight_layout()
plt.show()

Dieselbe Eigenschaft steuert später die Reihenfolge in Diagrammen und die Referenzkategorie in Modellen. Eine Bewertungsskala von schlecht bis ausgezeichnet gehört inhaltlich in dieser Reihenfolge und nicht alphabetisch; wer die Stufen setzt, bestimmt sie.

Häufige Falle: Zahlen, die als Faktor gespeichert sind, lassen sich nicht ohne Weiteres zurückrechnen. as.numeric liefert dann die internen Codes 1, 2, 3 statt der ursprünglichen Werte. Der sichere Weg führt über as.numeric(as.character(x)).

In Abbildung 1 erscheint links die Stufe weiss nicht mit dem Wert null, obwohl niemand so geantwortet hat. Warum ist das gewollt?

Weil die möglichen Stufen zum Faktor gehören und nicht aus den Daten abgeleitet werden
Richtig. Eine Antwortmöglichkeit bleibt Teil der Skala, auch wenn sie niemand gewählt hat. Für die Auswertung einer Umfrage ist genau das die vollständige Information.
Weil table immer alle Werte von null an zählt
table zählt über die bekannten Stufen. Bei Text gäbe es diese Stufe gar nicht.
Es ist ein Darstellungsfehler
Rechts im selben Bild fehlt die Stufe, und genau der Unterschied ist gemeint.

noten <- factor(c(5, 3, 4)). Was gibt as.numeric(noten) zurück?

5 3 4, die ursprünglichen Werte
Das wäre erwartbar und ist gerade nicht der Fall. Dafür braucht es den Umweg as.numeric(as.character(x)).
3 1 2, die internen Codes
Richtig. Der Faktor speichert nicht die Zahlen, sondern die Position in der sortierten Stufenliste 3, 4, 5. Die 5 steht an dritter Stelle.
1 2 3 in der Reihenfolge des Auftretens
Sortiert wird aufsteigend, nicht nach Auftreten. Sonst wäre die 5 die Eins.

Der Data Frame als Arbeitsstruktur

Ein einzelner Vektor beschreibt ein Merkmal. Daten bestehen aber aus mehreren Merkmalen zu denselben Objekten, und die haben selten denselben Typ: eine Kennnummer, eine Messgrösse, eine Kategorie. Genau dafür gibt es den Data Frame, eine Sammlung gleich langer Vektoren nebeneinander.

Die Konvention dahinter begleitet den ganzen Studiengang: Jede Zeile ist eine Beobachtung, jede Spalte ein Merkmal.

  • R
  • Python
df <- data.frame(
  id     = 1:5,
  wert   = c(2.5, 3.1, 4.0, 2.8, 3.6),
  gruppe = factor(c("A", "B", "A", "B", "A"))
)

str(df)      # Struktur: Spalten, Typen, erste Werte
'data.frame':   5 obs. of  3 variables:
 $ id    : int  1 2 3 4 5
 $ wert  : num  2.5 3.1 4 2.8 3.6
 $ gruppe: Factor w/ 2 levels "A","B": 1 2 1 2 1
df = pd.DataFrame({
    "id":     [1, 2, 3, 4, 5],
    "wert":   [2.5, 3.1, 4.0, 2.8, 3.6],
    "gruppe": pd.Categorical(["A", "B", "A", "B", "A"]),
})

df.info()

An der Ausgabe fällt auf, dass numerische und kategoriale Spalten verschieden zusammengefasst werden. Für Zahlen erscheinen Lage und Streubereich, für den Faktor die Häufigkeiten je Stufe. Was diese Kennzahlen bedeuten, ist Thema von L4 – Lage- und Streuungsmasse.

Einzelne Spalten und Zeilen lassen sich gezielt ansprechen:

df$wert                 # eine Spalte als Vektor
[1] 2.5 3.1 4.0 2.8 3.6
df[df$gruppe == "A", ]  # alle Zeilen der Gruppe A, alle Spalten
  id wert gruppe
1  1  2.5      A
3  3  4.0      A
5  5  3.6      A
mean(df$wert[df$gruppe == "A"])
[1] 3.366667

Der zweite Ausdruck zeigt das Muster, auf dem die spätere Datenaufbereitung aufbaut: Innen steht eine Bedingung, die für jede Zeile wahr oder falsch ist, aussen wird damit ausgewählt. Das Komma trennt Zeilen von Spalten, der leere Platz dahinter bedeutet alle Spalten.

Warum müssen alle Spalten eines Data Frames gleich lang sein, obwohl sie verschiedene Typen tragen dürfen?

Weil jede Zeile eine Beobachtung ist und sonst die Zuordnung verloren ginge
Richtig. Fehlte in einer Spalte ein Wert, wäre unklar, zu welcher Beobachtung die übrigen gehören. Deshalb steht dort NA statt nichts.
Weil R nur rechteckige Daten speichern kann
Kann es nicht nur; eine Liste nimmt beliebig lange Elemente auf. Der Data Frame verlangt es aus inhaltlichem Grund.
Aus Gründen der Geschwindigkeit
Der Grund ist die Bedeutung der Zeile, nicht die Verarbeitung.

Was ist der Unterschied zwischen df[2, ] und df[, 2]?

Das erste liefert eine Beobachtung, das zweite ein Merkmal
Richtig. Vor dem Komma stehen Zeilen, dahinter Spalten. df[2, ] ist die zweite Zeile, df[, 2] die zweite Spalte über alle Zeilen.
Beide liefern dasselbe, das Komma ist Formsache
Die Position des Kommas entscheidet, und die Ergebnisse haben verschiedene Formen.
Das zweite ist ungültig
Beide sind gültig. Ein leerer Platz bedeutet alle Elemente dieser Richtung.

Wenn die Tabelle nicht passt: Liste und Matrix

Nicht alles lässt sich als Tabelle darstellen. Das Ergebnis eines statistischen Tests etwa besteht aus einer Prüfgrösse, einem p-Wert, Freiheitsgraden und einem Beschreibungstext, alles von unterschiedlicher Länge. Dafür gibt es die Liste, die beliebige Objekte unter einem Namen sammelt. Der Data Frame ist genau genommen ein Sonderfall davon, nämlich eine Liste gleich langer Spalten.

ergebnis <- list(
  methode = "Beispiel",
  werte   = c(1.2, 3.4, 5.6),
  n       = 3
)

ergebnis$werte
[1] 1.2 3.4 5.6
str(ergebnis)
List of 3
 $ methode: chr "Beispiel"
 $ werte  : num [1:3] 1.2 3.4 5.6
 $ n      : num 3

Die Matrix ist das Gegenstück für rein numerische Daten mit Zeilen und Spalten, etwa eine Korrelationsmatrix. Sie trägt nur einen Typ und eignet sich deshalb für Rechnungen, nicht für gemischte Datensätze.

m <- matrix(1:6, nrow = 2)
m
     [,1] [,2] [,3]
[1,]    1    3    5
[2,]    2    4    6
dim(m)
[1] 2 3

Das Projekt statt des Arbeitsverzeichnisses

Ein Skript, das bei jemand anderem nicht läuft, scheitert erfahrungsgemäss an einem absoluten Pfad. Er verweist auf ein Verzeichnis, das nur auf einem einzigen Rechner existiert. Dasselbe passiert dem eigenen Skript nach einem Umzug der Daten.

Ein RStudio-Projekt löst das, indem es das Arbeitsverzeichnis auf den Projektordner festlegt. Pfade werden dann relativ dazu geschrieben und funktionieren überall, wo der Ordner als Ganzes liegt.

# schlecht: existiert nur auf einem Rechner
read.csv("C:/Users/mv/Desktop/Analyse/daten/messung.csv")

# gut: relativ zum Projektordner
read.csv("daten/messung.csv")

Der zweite Punkt betrifft den Zustand der Sitzung. RStudio bietet an, die Objekte beim Beenden zu speichern und beim Start wiederherzustellen. Das wirkt hilfreich, verdeckt aber Fehler: Ein Skript, das nur läuft, weil eine Variable noch aus der letzten Woche im Speicher liegt, ist nicht reproduzierbar. Die Einstellung gehört ausgeschaltet, und die Probe aufs Exempel ist ein Neustart mit leerer Umgebung.

Nützliche Kürzel in RStudio: neuer Codechunk, Chunk ausführen, Dokument rendern. Wer sie kennt, arbeitet spürbar flüssiger als über die Menüs.

Berichte, die nicht veralten

Eine Zahl, die von Hand aus der Konsole in ein Textdokument kopiert wurde, ist ab dem nächsten Datenstand falsch, und niemand sieht ihr das an. Quarto und R Markdown lösen das, indem Text und Rechnung in derselben Datei stehen. Beim Rendern wird der Code ausgeführt und das Ergebnis eingesetzt.

Der Baustein dafür heisst Chunk. Er beginnt mit drei Backticks und der Sprachangabe in geschweiften Klammern:

Der Mittelwert liegt bei 3.2.


::: {.cell}

```{.r .cell-code}
summary(df$wert)
```

::: {.cell-output .cell-output-stdout}

```
   Min. 1st Qu.  Median    Mean 3rd Qu.    Max. 
    2.5     2.8     3.1     3.2     3.6     4.0 
```


:::
