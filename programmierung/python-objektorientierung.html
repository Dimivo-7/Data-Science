Erklärung

Vorwissen: Python-Grundlagen für Dictionaries, die hier als Vergleich dienen, und Funktionen und Module in Python für Funktionen und Namensräume. Eine Methode ist nichts anderes als eine Funktion, die zu einem Objekt gehört.

Das Problem, bevor die Lösung kommt

Angenommen, mehrere Messreihen sind zu verwalten. Mit den bisherigen Mitteln entstehen ein Dictionary je Reihe und ein Satz Funktionen daneben:

reihe = {"name": "Drossel", "werte": [2.0, 4.0, 6.0], "einheit": "mm"}

def mittel(r):
    return sum(r["werte"]) / len(r["werte"])

print(mittel(reihe))
4.0

Das funktioniert und hat drei Schwächen. Nichts hindert daran, ein Dictionary ohne den Schlüssel werte an mittel zu übergeben; der Fehler fällt erst beim Aufruf auf. Die Funktionen liegen irgendwo im Modul und sind nicht als zusammengehörig erkennbar. Und wer eine Reihe von Hand baut, kann Schlüssel vergessen oder vertippen.

Eine Klasse bündelt die Daten und die Operationen darauf zu einer Einheit und legt beim Erzeugen fest, was vorhanden sein muss.

Klasse, Instanz, self

class Messreihe:
    einheit = "mm"                       # Klassenattribut, einmal fuer alle

    def __init__(self, name, werte):
        self.name = name                 # Instanzattribute, je Exemplar
        self.werte = werte

    def mittel(self):
        return sum(self.werte) / len(self.werte)

    def spannweite(self):
        return max(self.werte) - min(self.werte)

drossel = Messreihe("Drossel", [2.0, 4.0, 6.0])
ventil  = Messreihe("Ventil",  [1.5, 1.7, 9.0])

print(drossel.mittel(), ventil.spannweite())
4.0 7.5

Die Klasse ist der Bauplan, jedes erzeugte Objekt eine Instanz. __init__ läuft beim Erzeugen und legt die Instanzattribute an. self ist der Verweis auf das Exemplar, auf dem eine Methode gerade arbeitet, und steht deshalb als erster Parameter jeder Methode.

Der Unterschied zwischen Klassen- und Instanzattribut wird gerne übersehen und lässt sich zeigen:

print(drossel.einheit, ventil.einheit)     # beide teilen sich den Wert
mm mm
Messreihe.einheit = "cm"                    # Aenderung an der Klasse
print(drossel.einheit, ventil.einheit)     # wirkt auf alle
cm cm
drossel.einheit = "µm"                      # nur fuer dieses Exemplar
print(drossel.einheit, ventil.einheit)
µm cm

Für Konstanten ist das Klassenattribut richtig, für alles Zustandsbehaftete das Instanzattribut. Ein veränderliches Klassenattribut, etwa eine Liste, ist dieselbe Falle wie der veränderliche Defaultwert aus Funktionen und Module in Python.

Dunder-Methoden

Mit besonderen Methodennamen fügt sich eine eigene Klasse in die Sprache ein. Wer __str__ definiert, bestimmt, was print ausgibt; wer __len__ definiert, macht len() anwendbar.

class Messreihe:
    einheit = "mm"

    def __init__(self, name, werte):
        self.name = name
        self.werte = werte

    def mittel(self):
        return sum(self.werte) / len(self.werte)

    def __len__(self):
        return len(self.werte)

    def __str__(self):
        return f"{self.name}: {self.mittel():.2f} {self.einheit} (n={len(self)})"

m = Messreihe("Drossel", [2.0, 4.0, 6.0])
print(m)
Drossel: 4.00 mm (n=3)
print(len(m))
3

Ohne __str__ gäbe print nur die Speicheradresse aus. Mit ihr verhält sich das eigene Objekt wie ein eingebauter Typ, und genau das ist der Zweck.

Warum steht self in der Definition einer Methode, aber nicht im Aufruf m.mittel()?

Python setzt beim Aufruf das Objekt automatisch als erstes Argument ein
Richtig. m.mittel() wird intern zu Messreihe.mittel(m). Sichtbar wird der Mechanismus, wenn man die Methode über die Klasse aufruft.
self ist ein Schlüsselwort und wird ignoriert
Es ist ein gewöhnlicher Parametername; die Bezeichnung ist nur Konvention.
Der Aufruf ist unvollständig und funktioniert nur zufällig
Er ist die übliche und vorgesehene Schreibweise.

Was wäre die Folge, wenn werte = [] als Klassenattribut statt in __init__ stünde?

Nichts, es ist dieselbe Zuweisung an anderer Stelle
Der Ort entscheidet, ob das Objekt einmal für alle oder je Exemplar entsteht.
Alle Instanzen teilten sich dieselbe Liste
Richtig. Ein append in einem Objekt wäre in allen anderen sichtbar, und neue Objekte kämen bereits gefüllt zur Welt. Es ist derselbe Fehler wie der veränderliche Defaultwert bei Funktionen.
Die Klasse liesse sich nicht mehr instanziieren
Sie liesse sich problemlos instanziieren, und genau das macht den Fehler unauffällig.

Vererbung, sparsam eingesetzt

Vererbung erlaubt es, eine Klasse als Spezialisierung einer anderen zu schreiben und nur die Unterschiede zu formulieren:

class GewichteteMessreihe(Messreihe):
    def __init__(self, name, werte, gewichte):
        super().__init__(name, werte)      # der Teil, den die Basis erledigt
        self.gewichte = gewichte

    def mittel(self):                       # ueberschreibt die Basisversion
        return sum(w * g for w, g in zip(self.werte, self.gewichte)) / sum(self.gewichte)

g = GewichteteMessreihe("Drossel", [2.0, 4.0, 6.0], [1, 1, 3])
print(g)            # __str__ und __len__ stammen aus der Basisklasse
Drossel: 4.80 mm (n=3)
print(g.mittel())   # mittel kommt aus der abgeleiteten
4.8

Die Ausgabe zeigt beides: Die geerbten Methoden funktionieren unverändert, und __str__ verwendet automatisch die überschriebene Berechnung, weil es self.mittel() aufruft.

So elegant das ist, so schnell wird es überstrapaziert. Eine tiefe Hierarchie ist meist schwerer zu verstehen als eine flache Struktur, in der Objekte einander enthalten statt beerben. Die Prüffrage lautet, ob wirklich eine ist-ein-Beziehung vorliegt.

Der Vergleich zu R

R kennt mehrere Objektsysteme. S4 kommt der Sichtweise aus Python am nächsten, trennt aber Klassendefinition und Methode:

  • R
  • Python
setClass("Messreihe",
         representation(name = "character", werte = "numeric"))

setGeneric("mittel", function(obj) standardGeneric("mittel"))
[1] "mittel"
setMethod("mittel", "Messreihe", function(obj) mean(obj@werte))

m <- new("Messreihe", name = "Drossel", werte = c(2, 4, 6))
mittel(m)
[1] 4
class Kurz:
    def __init__(self, name, werte):
        self.name, self.werte = name, werte

    def mittel(self):
        return sum(self.werte) / len(self.werte)

print(Kurz("Drossel", [2, 4, 6]).mittel())
4.0

Der Unterschied ist mehr als Syntax. In Python gehört die Methode zum Objekt und wird darauf aufgerufen. In R gehört sie zur generischen Funktion, die anhand der Klasse ihres Arguments entscheidet, welche Umsetzung greift. Deshalb heisst es dort mittel(m) und nicht m.mittel().

Wann sich der Aufwand lohnt

Für die Datenarbeit gilt eine einfache Leitlinie. Der Analyseteil bleibt funktional und tabellenorientiert: Ein DataFrame plus Funktionen darauf ist klarer als eine eigene Klasse. Objektorientiert wird es dort, wo etwas wiederverwendbar gekapselt werden soll und einen Zustand mitführt, etwa ein Datenbankzugriff, ein Modellwrapper oder eine Stufe in einer Verarbeitungskette.

Wer eine Klasse schreibt, deren Objekte nur einmal erzeugt und deren Methoden nacheinander genau einmal aufgerufen werden, hat eine Funktion umständlich verpackt. Das ist das häufigste Muster für unnötige Objektorientierung.

Wozu dient super().__init__(...) in einer abgeleiteten Klasse?

Es ruft die Initialisierung der Basisklasse auf, damit deren Attribute gesetzt werden
Richtig. Ohne diesen Aufruf hätte das Objekt weder name noch werte, und jede geerbte Methode liefe ins Leere.
Es macht die Klasse überhaupt erst ableitbar
Ableitbar ist sie durch die Angabe in der Klammer der Klassendefinition.
Es kopiert die Methoden der Basisklasse
Kopiert wird nichts, die Methoden werden bei Bedarf dort gesucht.

__str__ steht nur in der Basisklasse, gibt bei einem abgeleiteten Objekt aber den gewichteten Mittelwert aus. Wie kommt das?

__str__ ruft self.mittel() auf, und self ist das abgeleitete Objekt
Richtig. Python sucht die Methode dort zuerst und findet die überschriebene Version. Dieses Verhalten heisst dynamische Bindung und ist der eigentliche Nutzen der Vererbung.
Die abgeleitete Klasse hat __str__ stillschweigend überschrieben
Sie definiert es gar nicht, sondern erbt es unverändert.
Es ist ein Zufall der Reihenfolge
Das Verhalten ist festgelegt und verlässlich.

Typische Aufgaben

Klasse mit Konstruktor und lesbarer Darstellung

class Messung:
    def __init__(self, wert, einheit):
        self.wert = wert
        self.einheit = einheit

    def __repr__(self):
        return f"Messung({self.wert}, {self.einheit})"

Objekte vergleichbar und sortierbar machen

from dataclasses import dataclass, field

@dataclass(order=True)
class Messung:
    wert: float
    einheit: str = field(compare=False)

Von einer Klasse erben und den Konstruktor erweitern

class GewichteteMessung(Messung):
    def __init__(self, wert, einheit, gewicht):
        super().__init__(wert, einheit)
        self.gewicht = gewicht

Prüfen, was ein Objekt ist und kann

isinstance(m, Messung)
hasattr(m, "wert")
vars(m)

Dasselbe in R, wo Klassen anders gedacht sind

messung <- function(wert, einheit) {
  structure(list(wert = wert, einheit = einheit), class = "messung")
}
print.messung <- function(x, ...) cat("Messung:", x$wert, x$einheit, "\n")
