Erklärung

Vorwissen: Python-Grundlagen, insbesondere der Unterschied zwischen veränderlichen und unveränderlichen Objekten. Er erklärt die wichtigste Falle dieses Themas.

Wann eine Funktion fällig ist

Die Faustregel ist simpel: Sobald dieselbe Folge von Schritten ein zweites Mal auftaucht, gehört sie in eine Funktion. Der Grund ist weniger das Tippen als die Korrektur. Steht eine Berechnung dreimal im Skript und stellt sich als falsch heraus, muss man alle drei Stellen finden. Steht sie einmal, genügt eine Änderung.

Der zweite Grund ist die Benennung. Eine Funktion mit einem guten Namen macht aus fünf Zeilen Code eine Zeile, die sagt, was passiert.

Parameter und ihre Reihenfolge

def kennzahlen(werte, runden=2, einheit="mm"):
    mittel = sum(werte) / len(werte)
    return f"{round(mittel, runden)} {einheit}"

print(kennzahlen([12.34, 15.67, 11.02]))          # nur das Noetige
13.01 mm
print(kennzahlen([12.34, 15.67, 11.02], 1))       # nach Position
13.0 mm
print(kennzahlen([12.34, 15.67, 11.02], einheit="cm"))   # nach Name
13.01 cm

Positionsparameter werden über die Reihenfolge zugeordnet, Schlüsselwort- parameter über den Namen. Der Aufruf mit Namen ist bei mehr als zwei Argumenten fast immer die bessere Wahl, weil er sich ohne Blick auf die Definition lesen lässt.

Die Falle mit veränderlichen Defaultwerten

Diese Stelle kostet erfahrungsgemäss einmal im Leben einen halben Tag. Der Defaultwert wird einmal bei der Definition ausgewertet, nicht bei jedem Aufruf. Ist er veränderlich, teilen sich alle Aufrufe dasselbe Objekt:

def sammeln_falsch(wert, bisher=[]):
    bisher.append(wert)
    return bisher

print(sammeln_falsch(1))
[1]
print(sammeln_falsch(2))     # erwartet [2], kommt aber [1, 2]
[1, 2]
print(sammeln_falsch(3))
[1, 2, 3]

Der richtige Weg verwendet None als Signal und legt das Objekt im Funktionsrumpf an:

def sammeln(wert, bisher=None):
    if bisher is None:
        bisher = []
    bisher.append(wert)
    return bisher

print(sammeln(1))
[1]
print(sammeln(2))
[2]

Merkregel: Als Defaultwert taugen nur unveränderliche Objekte, also Zahlen, Zeichenketten, Tupel, True, False und None. Alles andere gehört in den Rumpf.

Beliebig viele Argumente

*args sammelt weitere Positionsargumente in einem Tupel, **kwargs weitere Schlüsselwortargumente in einem Dictionary. Gebraucht wird das vor allem beim Durchreichen an eine andere Funktion:

def protokolliert(funktion, *args, **kwargs):
    print(f"rufe {funktion.__name__} mit {args} und {kwargs}")
    return funktion(*args, **kwargs)

protokolliert(kennzahlen, [1.0, 2.0, 3.0], einheit="kg")
rufe kennzahlen mit ([1.0, 2.0, 3.0],) und {'einheit': 'kg'}
'2.0 kg'

Der Stern erfüllt hier zwei Rollen: In der Definition sammelt er ein, im Aufruf packt er wieder aus.

Eine Funktion ist als def sammeln(wert, bisher=[]) definiert. Der erste Aufruf liefert [1], der zweite [1, 2]. Warum?

Der Defaultwert wurde einmal bei der Definition erzeugt und wird geteilt
Richtig. Die leere Liste hängt seither an der Funktion, und jeder Aufruf ohne zweites Argument hängt daran weiter an.
Python merkt sich die vorherigen Aufrufe
Einen solchen Mechanismus gibt es nicht. Es liegt allein am geteilten Objekt.
Die Funktion ruft sich selbst auf
Jeder Aufruf ist unabhängig, nur das Defaultobjekt ist es nicht.

Wann ist *args gerechtfertigt und wann ein Zeichen für unklares Design?

Gerechtfertigt beim Durchreichen an eine andere Funktion
Richtig, etwa wenn man deren Signatur nicht wiederholen will, oder bei beliebig vielen gleichartigen Werten. Verdächtig wird es, wenn damit verdeckt wird, dass eine Funktion zu viele verschiedene Dinge tut.
Immer gerechtfertigt, es macht Funktionen flexibel
Flexibilität ohne erkennbare Signatur macht den Aufruf unlesbar.
Nie, benannte Parameter sind immer besser
Beim Weiterreichen wären sie eine Verdopplung, die bei jeder Änderung nachgezogen werden müsste.

Namensräume

Innerhalb einer Funktion angelegte Namen sind lokal und verschwinden mit dem Aufruf. Gelesen wird von innen nach aussen; geschrieben wird ohne ausdrückliche Erklärung immer lokal.

zaehler = 0

def liest_nur():
    return zaehler + 1        # aeusserer Wert wird gelesen

def schreibt_lokal():
    zaehler = 99              # legt einen NEUEN lokalen Namen an
    return zaehler

print(liest_nur(), schreibt_lokal(), zaehler)
1 99 0

Der äussere Zähler bleibt unverändert, obwohl die zweite Funktion ihm scheinbar etwas zuweist. Das ist gewollt: Versteckte Seiteneffekte sind die häufigste Ursache schwer auffindbarer Fehler, und Python macht sie zum Sonderfall statt zum Normalfall.

  • R
  • Python
zaehler <- 0

liest_nur <- function() zaehler + 1
schreibt_lokal <- function() { zaehler <- 99; zaehler }

c(liest_nur(), schreibt_lokal(), zaehler)
[1]  1 99  0
zaehler = 0

def liest_nur():
    return zaehler + 1

def schreibt_lokal():
    zaehler = 99
    return zaehler

print([liest_nur(), schreibt_lokal(), zaehler])
[1, 99, 0]

Beide Sprachen verhalten sich hier gleich. In R heisst der Mechanismus lexical scoping, in Python LEGB-Regel, gemeint ist dasselbe.

Funktionen sind Objekte

Eine Funktion lässt sich einer Variablen zuweisen, an eine andere Funktion übergeben und aus einer zurückgeben. Darauf beruhen map, filter und das Argument key beim Sortieren.

  • R
  • Python
messungen <- list(c(1, 2, 3), c(10, 20), c(5))

sapply(messungen, mean)                 # Funktion als Argument
[1]  2 15  5
sapply(messungen, length)
[1] 3 2 1
leute <- list(list(name = "Ada", jahr = 1815),
              list(name = "Alan", jahr = 1912))
sapply(leute, function(p) p$name)
[1] "Ada"  "Alan"
messungen = [[1, 2, 3], [10, 20], [5]]

print([sum(m) / len(m) for m in messungen])
[2.0, 15.0, 5.0]
print(list(map(len, messungen)))
[3, 2, 1]
leute = [{"name": "Ada", "jahr": 1815}, {"name": "Alan", "jahr": 1912}]
print(sorted(leute, key=lambda p: p["jahr"])[0]["name"])
Ada

lambda ist eine Kurzschreibweise für eine namenlose Funktion mit einem einzigen Ausdruck. Für alles Längere ist eine benannte Funktion lesbarer, und für die meisten map-Aufrufe ist eine Comprehension die klarere Wahl.

Vom Skript zum Modul

Sobald eine Datei wächst, lohnt die Aufteilung. Jede .py-Datei ist ein Modul und kann importiert werden. Der Block am Ende trennt den ausführbaren Teil vom importierbaren:

# datei: kennzahlen.py

def mittel(werte):
    return sum(werte) / len(werte)

if __name__ == "__main__":
    # laeuft nur beim direkten Aufruf, nicht beim Import
    print(mittel([1, 2, 3]))

Ohne diesen Block würde beim Import der Testcode mitlaufen. Der Name __main__ wird nur gesetzt, wenn die Datei direkt gestartet wird; beim Import steht dort der Modulname.

print(__name__)      # in diesem Dokument nicht "__main__"
__main__

Für die Datenarbeit hat sich diese Aufteilung bewährt: Funktionen in ein Modul, das versioniert und getestet wird, und ein Notebook, das diese Funktionen aufruft und die Erzählung liefert. So bleibt die Logik prüfbar und das Dokument lesbar.

Ein Skript enthält Testaufrufe am Dateiende und wird von einer anderen Datei importiert. Was passiert ohne if __name__ == "__main__"?

Die Testaufrufe laufen beim Import mit
Richtig. Beim Import wird der gesamte Dateiinhalt ausgeführt. Das kostet Zeit, erzeugt unerwünschte Ausgaben und kann im schlimmsten Fall Dateien überschreiben.
Nichts, Funktionen werden beim Import nur definiert
Definitionen ja, aber Aufrufe auf oberster Ebene werden ausgeführt.
Der Import schlägt fehl
Er gelingt, nur eben mit Nebenwirkungen.

Warum ist sorted(leute, key=lambda p: p["jahr"]) einer eigenen Sortierschleife vorzuziehen?

Weil Lambda-Ausdrücke schneller sind
Der Gewinn liegt nicht am Lambda, sondern an der geprüften Sortierfunktion dahinter.
Weil die Absicht in einer Zeile steht und der Sortiercode geprüft ist
Richtig. Eine eigene Schleife müsste Stabilität, Sonderfälle und Effizienz nachbilden, ohne dass daraus etwas gewonnen wäre.
Weil eigene Schleifen in Python verboten sind
Sie sind erlaubt, nur hier unnötig.
