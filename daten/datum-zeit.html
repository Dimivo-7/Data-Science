Datum und Zeit

Data Wrangling
R
Python
Zeitstempel parsen, rechnen, Zeitzonen und typische Stolpersteine.

Diese Seite ist ein Entwurf. Der Inhalt steht, ist aber noch nicht durchgeprüft.

Kernideen

  • Ein Datum ist ein eigener Typ, keine Zeichenkette und keine Zahl
  • Umgewandelt wird früh, am besten direkt beim Import
  • Das Format muss angegeben werden, sonst rät die Bibliothek
  • Differenzen zwischen Zeitpunkten haben eine Einheit, die man mitliest
  • Zeitzonen und Sommerzeit sind die Quelle der unangenehmsten Fehler

Erklärung

Vorwissen: Datenimport und Formate, denn die Umwandlung gehört dorthin, und Data Wrangling für das Gruppieren nach Zeitabschnitten. Für Reihen, bei denen die Reihenfolge selbst Information trägt, siehe Zeitreihen.

Warum Text als Datum gefährlich ist

Solange ein Datum als Zeichenkette vorliegt, wird alphabetisch verglichen und sortiert. Der 10. Januar liegt dann vor dem 2. Februar, weil die Ziffer 1 vor der 2 steht. Ebenso scheitert jede Rechnung: die Differenz zwischen zwei Zeichenketten ist nicht definiert, und eine Gruppierung nach Monat gruppiert nach Text.

  • R
  • Python
roh <- c("05.01.2026", "10.01.2026", "02.02.2026")

sort(roh)                       # alphabetisch, also falsch
[1] "02.02.2026" "05.01.2026" "10.01.2026"
datum <- dmy(roh)               # Tag, Monat, Jahr
sort(datum)
[1] "2026-01-05" "2026-01-10" "2026-02-02"
class(datum)
[1] "Date"
roh = pd.Series(["05.01.2026", "10.01.2026", "02.02.2026"])

print(roh.sort_values().tolist())        # alphabetisch, also falsch
['02.02.2026', '05.01.2026', '10.01.2026']
datum = pd.to_datetime(roh, format="%d.%m.%Y")
print(datum.sort_values().tolist())
[Timestamp('2026-01-05 00:00:00'), Timestamp('2026-01-10 00:00:00'), Timestamp('2026-02-02 00:00:00')]
print(datum.dtype)
datetime64[us]

In R heissen die Parser nach der Reihenfolge der Bestandteile: ymd, dmy, mdy, für Zeitstempel ymd_hms. In Python nimmt pd.to_datetime ein format in der Schreibweise mit Prozentzeichen. Ohne Formatangabe raten beide, und das Raten geht bei Tagen bis zwölf schief, weil 03.04.2026 sowohl der 3. April als auch der 4. März sein kann. Wer das Format kennt, gibt es an.

Bestandteile herausziehen und gruppieren

  • R
  • Python
d <- ymd("2026-03-15")

year(d); month(d); day(d)
[1] 2026
[1] 3
[1] 15
wday(d, label = TRUE, week_start = 1)
[1] Sun
Levels: Mon < Tue < Wed < Thu < Fri < Sat < Sun
isoweek(d)
[1] 11
floor_date(d, unit = "month")     # auf den Monatsanfang abrunden
[1] "2026-03-01"
d = pd.Timestamp("2026-03-15")

print(d.year, d.month, d.day)
2026 3 15
print(d.day_name())
Sunday
print(d.isocalendar().week)
11
print(d.to_period("M").start_time)
2026-03-01 00:00:00

Für eine Auswertung je Monat wird nicht der Monatsname als Text gebildet, sondern auf den Monatsanfang abgerundet. Der Text verliert das Jahr, und Januar 2025 landet dann in derselben Gruppe wie Januar 2026.

Rechnen mit Zeitpunkten

  • R
  • Python
start <- ymd("2026-01-05")
ende  <- ymd("2026-03-15")

ende - start                          # Differenz mit Einheit
Time difference of 69 days
as.numeric(ende - start, units = "days")
[1] 69
start + days(30)
[1] "2026-02-04"
start %m+% months(1)                  # monatsweise, ohne Ueberlauf
[1] "2026-02-05"
start = pd.Timestamp("2026-01-05")
ende = pd.Timestamp("2026-03-15")

print(ende - start)                   # Timedelta
69 days 00:00:00
print((ende - start).days)
69
print(start + pd.Timedelta(days=30))
2026-02-04 00:00:00
print(start + pd.DateOffset(months=1))
2026-02-05 00:00:00

Die Differenz ist in beiden Sprachen ein eigener Typ mit Einheit, nicht einfach eine Zahl. Wer sie weiterrechnet, wandelt sie ausdrücklich um und legt die Einheit fest; sonst hängt das Ergebnis davon ab, welche Einheit die Bibliothek gewählt hat.

Der Zusatz %m+% in R und DateOffset in Python addieren Monate, ohne über das Monatsende hinauszulaufen: der 31. Januar plus ein Monat ergibt den 28. oder 29. Februar, nicht den 3. März.

Zeitzonen

Ein Zeitstempel ohne Zeitzone ist mehrdeutig, sobald Daten aus mehreren Quellen zusammenkommen. Zwei Regeln vermeiden die meisten Probleme: intern in UTC speichern und rechnen, erst für die Ausgabe in die lokale Zone umwandeln.

  • R
  • Python
t <- ymd_hms("2026-03-29 01:30:00", tz = "UTC")

with_tz(t, "Europe/Zurich")     # derselbe Zeitpunkt, andere Darstellung
[1] "2026-03-29 03:30:00 CEST"
force_tz(t, "Europe/Zurich")    # andere Interpretation, anderer Zeitpunkt
[1] "2026-03-29 01:30:00 CET"
t = pd.Timestamp("2026-03-29 01:30:00", tz="UTC")

print(t.tz_convert("Europe/Zurich"))    # derselbe Zeitpunkt, andere Darstellung
2026-03-29 03:30:00+02:00
print(t.tz_localize(None))              # Zeitzone entfernen, Wert bleibt
2026-03-29 01:30:00

Der Unterschied zwischen Umwandeln und Festlegen ist der Kern: with_tz und tz_convert beschreiben denselben Moment in einer anderen Zone, force_tz und tz_localize behaupten, dass die abgelesene Uhrzeit in einer anderen Zone galt, und verschieben damit den Zeitpunkt selbst.

Die Umstellung auf Sommerzeit macht zusätzlich zwei Dinge kaputt: In der Umstellungsnacht gibt es eine Stunde, die nicht existiert, und im Herbst eine, die zweimal vorkommt. Deshalb ist ein Tag nicht immer 24 Stunden lang, und eine Differenz in Tagen ist nicht immer das Vielfache von 24 Stunden.

Ein Datensatz enthält die Spalte datum als Text im Format 03.04.2026, und der Import hat sie automatisch umgewandelt. Warum ist das ein Risiko?

Kein Risiko, die Erkennung ist zuverlässig
Sie ist es genau dann nicht, wenn beide Lesarten möglich sind.
Bei Tageszahlen bis zwölf sind Tag und Monat vertauschbar
Richtig. 03.04.2026 kann der 3. April oder der 4. März sein. Die automatische Erkennung wählt eine Lesart, oft je nach Spracheinstellung, und der Fehler fällt erst bei einer Auswertung nach Monat auf.
Weil Text grundsätzlich nicht umgewandelt werden darf
Umgewandelt gehört er unbedingt, nur mit ausdrücklichem Format.

Eine Auswertung gruppiert Umsätze nach dem Monatsnamen, den sie aus dem Datum gebildet hat. Was geht dabei schief?

Gleiche Monate verschiedener Jahre landen in derselben Gruppe
Richtig. Der Name enthält das Jahr nicht mehr. Richtig ist, auf den Monatsanfang abzurunden oder Jahr und Monat gemeinsam zu gruppieren.
Die Sortierung wird alphabetisch
Das passiert zusätzlich, ist aber nur ein Darstellungsproblem.
Nichts, das ist der übliche Weg
Er ist üblich und trotzdem falsch, sobald mehr als ein Jahr in den Daten steckt.

Typische Aufgaben

Beim Import direkt umwandeln

  • R
  • Python
readr::read_csv("daten.csv", col_types = readr::cols(
  datum = readr::col_date(format = "%d.%m.%Y")
))
pd.read_csv("daten.csv", parse_dates=["datum"], dayfirst=True)

Nach Monat oder Woche zusammenfassen

  • R
  • Python
df |>
  dplyr::mutate(monat = lubridate::floor_date(datum, "month")) |>
  dplyr::summarise(summe = sum(umsatz), .by = monat)
df.groupby(df["datum"].dt.to_period("M"))["umsatz"].sum()

Eine Zeitachse ohne Lücken erzeugen

  • R
  • Python
seq(as.Date("2026-01-01"), as.Date("2026-12-31"), by = "day")
pd.date_range("2026-01-01", "2026-12-31", freq="D")

Alter oder Dauer in Jahren berechnen

  • R
  • Python
as.numeric(lubridate::interval(geburtstag, Sys.Date()) / lubridate::years(1))
(pd.Timestamp.today() - geburtstag).dt.days / 365.25

Unix-Zeitstempel umwandeln

  • R
  • Python
as.POSIXct(1767225600, origin = "1970-01-01", tz = "UTC")
pd.to_datetime(1767225600, unit="s", utc=True)

Für die Ausgabe formatieren

  • R
  • Python
format(datum, "%d.%m.%Y")
datum.dt.strftime("%d.%m.%Y")
